# Canonical test vectors

`vectors.json` is the **interoperability contract** for arxid. Every
implementation, in every language, validates against this exact file. An id
obfuscated by one conforming implementation deobfuscates identically in all the
others because they all agree with these vectors.

**A port that disagrees with `vectors.json` is a bug in the port**, not an
acceptable variation.

## Why vectors and not just round-trip tests

Round-trip (`deobfuscate(obfuscate(x)) == x`) is symmetric. A port that gets the
wrapping width wrong, sign-extends a shift, or truncates the 64-bit key
schedule will still round-trip perfectly with itself while producing completely
different values from every other implementation. Only known-answer vectors
catch that.

SPEC.md section 8 lists the exact places ports diverge. Read it before porting.

## Format

A JSON array. Each element is one known-answer test:

```json
{ "key": 0, "id": 42, "obfuscated": 598094900732, "encoded": "AWqXFbI" }
```

| Field | Type | Meaning |
|---|---|---|
| `key` | integer, decimal | The 64-bit unsigned key. **Up to 2^64-1.** |
| `id` | integer, decimal | The input, in `[0, 2^40-1]`. |
| `obfuscated` | integer, decimal | Expected `obfuscate(id, key)`, in `[0, 2^40-1]`. |
| `encoded` | string, 7 chars | Expected `to_base62(obfuscated)`. |

Assertions your test must make, for every row:

```
obfuscate(id, key)          == obfuscated
deobfuscate(obfuscated, key) == id
to_base62(obfuscated)        == encoded
from_base62(encoded)         == obfuscated
```

### Reading `key` safely

`id` and `obfuscated` are at most 2^40-1 and fit exactly in any numeric type,
including IEEE-754 doubles.

**`key` does not.** It ranges over the full `u64`. In a language whose JSON
parser produces floats (JavaScript, and any `JSON.parse`-style parser), reading
`key` as a number silently rounds it. Parse it as a 64-bit integer or a bigint:
read the raw digits from the text and convert, or use a parser with an
arbitrary-precision integer mode. The TypeScript port does the former; see
`impl/ts/test/vectors.test.ts`.

## Coverage

61 vectors, generated by the Rust reference implementation.

**Keys** (5 distinct): `0`, `1`, `0x9E3779B97F4A7C15` (the golden constant),
`0xD1B54A32D192ED03` (an arbitrary large key), and `0x8000000000000000` (only
the top bit set - a port that truncated the key to 32 bits would read it as 0
and fail here).

`u64::MAX` is deliberately absent: the key schedule maps `key` and `!key` to the
same permutation (SPEC.md section 2.1), so its rows would just duplicate those
of key `0` and test nothing.

**Ids**: the domain edges `0`, `1`, `2`, `MAX_ID/2`, `MAX_ID-1`, `MAX_ID`, plus
ordinary values `42`, `1000`, `12345`, `1000000` - each under all 5 keys.

**Non-enumerability**: ids `100` through `110` under the golden key, a run of
consecutive inputs. Their outputs are not neighbours; that is the whole point of
the library, asserted directly on the published vectors.

## Regenerating

The vectors are **never written by hand**. They are produced by running the
reference implementation:

```sh
cd impl/rust
cargo run --example gen_vectors > ../../vectors/vectors.json
```

If regenerating changes any existing value, you have changed the algorithm.
That requires a **new spec version and a new vector file**, never a silent
update. See SPEC.md section 10.

## Adding a port

See [`CONTRIBUTING.md`](../CONTRIBUTING.md). In short: reimplement
[`spec/SPEC.md`](../spec/SPEC.md) natively, load this file in your test suite,
assert all four directions above for every row, and add a CI job that runs it.
